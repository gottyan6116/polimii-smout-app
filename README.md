# 移住・関係人口 政策支援（共同サービス検討用デモ）

SMOUTデータ活用構想にもとづく、自治体職員向け「移住・関係人口政策支援AI」の商談用 PoC です。
株式会社カヤックとの共同事業を検討するための **非公式・構想段階のデモ** であり、正式な共同製品ではありません。

> **表示しているデータはすべてデモ用の架空データです。** 実在の自治体・SMOUTの実データではありません。
> 分析コメントと文書は **ルールベースのデモエンジン** で作成しており、生成AIは使用していません。

---

## 1. 概要と事業コンセプト

SMOUTが持つ「地域・人・関心」のデータと、Polimillの行政向けAI基盤「Qommons ONE」を組み合わせ、
自治体職員の **施策評価 → 改善提案 → 次年度計画 → 行政文書作成** までを一続きで支援します。

- **価値A：施策評価・改善の高度化** — SMOUTの活動実績と自治体KPIから、成果・課題・改善余地を把握する
- **価値B：地域・人材・関心分析** — 年代・関心テーマ・移住検討段階から、次に注力すべきターゲットと施策の方向性を検討する
- **差別化** — 分析ダッシュボードで終わらせず、成果報告書・事業計画書などの行政文書まで作り、編集・出力できること

連携方式は Qommons ONE の **データプロバイダー型（モデルA）** を想定しています（カヤックから許諾されたデータをPolimillが受領・処理し、データ連携済みのアプリを自治体職員に提供）。自治体職員がCSVを手動アップロードする画面はありません。

## 2. 想定利用者

- 移住・定住、関係人口施策を所管する自治体職員（企画課・地域振興課など）
  - パターン1：SMOUTを利用している自治体（自自治体の活動実績で評価できる）
  - パターン2：SMOUTを利用していない自治体（参考集計で地域分析・ターゲット検討を行う。自治体横断データの提供可否は未確認）

## 3. 主要機能と画面構成

| 画面 | パス | 主な内容 |
|---|---|---|
| ホーム：政策支援ワークスペース | `/` | 2つの主要フロー（評価・報告／次年度立案）、直近の文書、利用可能なデータ、分析機能へのショートカット |
| 施策評価・成果報告 | `/evaluation` | 自治体KPIの目標・実績・達成率・判定（達成／未達成／判断不能）、SMOUT活動実績の推移、施策別の成果、分析コメント、成果報告書の作成 |
| 地域・人材・関心分析 | `/insights` | 年代別構成、移住検討段階、関心テーマのランキング、年代×テーマのヒートマップ、地域別比較、示唆。データ範囲・地域・年代のフィルター |
| 課題分析・改善提案 | `/improvements` | 課題ごとに「確認できた事実／考えられる仮説／推奨するアクション／検証が必要な事項」を分けて表示。改善施策候補の優先順位、採用→次年度計画へ反映 |
| 次年度の施策立案 | `/planning` | 左に分析根拠、右に計画案。重点ターゲットの編集、施策の選択・編集（内容・時期・担当・KPI目標案）、スケジュール、KPIの根拠 |
| 行政文書の作成・編集 | `/documents`、`/documents/[id]` | 5種のテンプレート、下書き生成、編集・保存・再編集、分析結果の挿入、数値の照合、未確認項目の警告、最終確認チェックリスト、Word（.docx）出力、印刷・PDF保存 |

作成できる文書：成果報告書／次年度事業計画書／施策改善提案書／地域・関心分析レポート／庁内・議会向け説明資料（原稿）

画面上部の「対象自治体」「対象年度」は全画面で共有され、切り替えるとKPI・分析・改善案・文書内容がすべて変わります。

## 4. 技術スタック

- Next.js 16（App Router）／React 19／TypeScript（strict）
- Tailwind CSS v4、Radix UI（Tabs）、lucide-react（アイコン）
- Recharts（推移グラフ）、docx（Word生成、ブラウザ上で生成）
- フォント：Noto Sans JP（next/font）
- 保存：ブラウザの localStorage（デモ用）

外部DB・認証サービス・有料API・外部SaaSは使用していません。

## 5. ローカル起動

Node.js 20.9 以上（開発時は v24 で確認）。

```bash
npm install
npm run dev        # http://localhost:3000
npm run lint       # ESLint
npx tsc --noEmit   # 型チェック
npm run build      # 本番ビルド
```

### 環境変数

**不要です。** APIキーなしで全機能が動作します。
将来LLMを接続する場合は、サーバー側の環境変数（例：`ANTHROPIC_API_KEY`）でのみ扱い、クライアントに露出させないでください（`src/lib/generation/engine.ts` 参照）。

## 7. デモデータの構造

| データ | 内容 | 粒度 | 出典表示 |
|---|---|---|---|
| 自治体マスタ | サンプルA町（SMOUT利用あり）、サンプルB市（SMOUT未利用）。いずれも架空 | 自治体 | — |
| 年度 | 令和6年度・令和7年度（通年）、令和8年度（4〜9月、年度途中） | 会計年度 | — |
| 施策（SMOUT掲載プロジェクト） | A町の5施策（住まい・仕事・体験・相談・継業） | 施策 | — |
| SMOUT活動実績 | 興味ある・応募したい・スカウト・返信ありの **件数** | 施策×月 | SMOUT 活動実績（項目は公開情報で確認／提供方法は未確定） |
| 施策目標 | 興味ある・応募したいの年度目標（件数） | 施策×年度 | — |
| 自治体KPI | 移住相談件数、転入者数、お試し住宅利用組数など。目標・実績、欠損（データなし）と 0 を区別 | 自治体×年度 | 自治体保有データ |
| 反応者の属性 | 年代別・移住検討段階別の **ユニーク人数** | 自治体×年度 | 項目は公開情報で確認／提供方法は未確定 |
| 年代×関心テーマ | クロス集計（人数、テーマは複数選択） | 自治体×年度 | **提供可否 未確認** |
| 参考集計 | 地域ブロック別の年代・段階・テーマ | 地域×年度 | **提供可否 未確認** |

データ品質のルール（実装済み）：
- KPIとグラフ・文書の数値は同じ算出ロジック（`lib/analysis`）から出すため一致する
- 算出できない指標は「データなし」「算出不可」と表示し、0 と区別する
- 件数（延べ）と人数（ユニーク）を区別し、件数を人数として扱わない
- 年度途中の年度は達成判定をせず「判断不能」（進捗率のみ）
- 前年比の増減を施策の効果と断定しない（画面・文書に注記）
- SMOUT未利用の自治体には架空の実績を生成しない
- 計算式：達成率＝実績÷目標×100、応募転換率＝応募したい÷興味ある×100（件数ベース）、返信率＝返信あり÷（応募したい＋スカウト）×100、前年度比は同じ月数の期間で比較、選択率＝テーマ選択人数÷ユニーク人数×100

## 8. データの出典・仮定・未確認項目

- SMOUT管理画面で「興味ある数」「応募したい数」「スカウト数」「返信あり数」「返信あり率」、ユーザーデータ（移住ステップ・年齢層、直近3か月）が確認できることは、SMOUTの公開ヘルプ「データ活用」で確認しています（2026-11-09確認）。**ただし、これらをPolimillへ提供する方法・粒度・期間は未確定です。**
- 年代×関心テーマのクロス集計、自治体横断（地域別）の参考集計は、**SMOUTから提供可能かどうか未確認** です。デモでは機能を示すために架空データを使用しています。
- 「返信率」の母数（応募したい＋スカウト）は公開ヘルプの「返信あり率」の説明に合わせていますが、正式な定義は要確認です。
- KPI目標案は、根拠データがある場合のみ数値を示し（例：町内平均の応募転換率）、根拠がない場合は「要設定」としています。

詳細は [docs/DATA_REQUIREMENTS.md](docs/DATA_REQUIREMENTS.md) を参照してください。

## 9. 今後必要になるSMOUTからのデータ提供仕様（要約）

1. プロジェクト別・月次の活動件数（興味ある／応募したい／スカウト／返信あり）と、件数の定義（延べ・重複の扱い）
2. 反応者の属性（年代・移住ステップ・関心テーマ）のユニーク人数と、集計の最小単位（少数セルの秘匿ルール）
3. 自治体横断の地域別集計の可否、利用範囲（SMOUT未利用自治体への提供可否）
4. 提供方式（定期ファイル連携／API／MCPサーバー）、更新頻度、履歴期間
5. 二次利用・再提供の範囲、個人情報を含まない形式であることの確認

## 10. 本番化する場合の実装課題（未実装）

- 自治体ごとのテナント分離、認証・認可（職員・管理者の権限）
- データ利用許諾の範囲チェック（自治体ごとに参照できるデータを制御）
- 監査ログ（誰がどのデータを参照し、どの文書を出力したか）
- サーバー側のデータ取り込み（バッチ/API）と国内リージョンでの保管
- 文書の保存先（現在は localStorage のみ。端末・ブラウザをまたいだ共有不可）
- LLM連携（サーバー側実装、数値の照合、出力の記録）
- Qommons ONE の搭載要件（セキュリティ・品質・運用）への適合確認

**localStorage への保存は本番の認証・アクセス制御・データ保護の代わりになりません。** 詳細は [docs/PRODUCT_SCOPE.md](docs/PRODUCT_SCOPE.md)。

## 11. Vercel への接続手順

1. Vercel にログインし「Add New… → Project」
2. GitHub リポジトリ `gottyan6116/polimii-smout-app` を Import
3. Framework Preset は「Next.js」（自動判定）。Build Command・Output は既定のまま
4. 環境変数は不要
5. 「Deploy」

`main` への push で自動デプロイされます。デモ用のため、公開範囲（Vercel の Deployment Protection 等）は商談相手に合わせて設定してください。

## 12. 商談での推奨デモ手順（各1〜2分）

**体験1：施策の成果から報告書が完成する（サンプルA町・令和7年度）**
1. ホームで「施策評価を始める」
2. KPI表で「達成／未達成／判断不能」と定義（件数・人数）を見せる。関係人口登録者数は「データなし」で判断不能になることを示す
3. 施策別の成果で、関心はあるが応募につながっていない施策を示す
4. 分析コメントで「事実」と「仮説」が分かれていることを示す
5. 「成果報告書を作成する」→ 下書きが開く → 右側の「未確認項目」「数値の照合」を見せる
6. 「Word（.docx）でダウンロード」または「印刷・PDFで保存」

**体験2：関心・人材データから次年度施策案が完成する**
1. ホームで「関心分析から始める」→ 反応者は50代が最多、想定ターゲット（20〜30代）とのずれ、伸びているテーマを示す
2. 「課題と改善施策を確認」→ 施策候補を2〜3件選び「次年度計画に反映する」
3. 計画画面で施策を「編集」し、KPI目標案を入力（根拠が表示される）
4. 「次年度事業計画書を作成する」→ 編集・出力

**補足**：画面上部で「サンプルB市（SMOUT未利用）」に切り替えると、SMOUTの実績欄が「データなし」となり、参考集計（提供可否未確認）で分析する流れになります。年度を「令和8年度（上期）」にすると年度途中の扱い（判断不能・進捗率）を確認できます。
